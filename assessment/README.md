# Current Profile Data Dictionary

`csf-2.0-current-profile.csv` holds the Current and Target Profile for all 106 active CSF 2.0 subcategories, one row each. Rules governing how each column is filled are defined in [docs/scope-and-methodology.md](../docs/scope-and-methodology.md). The definitions below describe the schema and point to the governing section.

Source for the framework columns is the CSF 2.0 Core exported from the NIST Cybersecurity and Privacy Reference Tool, final version. The NIST export lists 79 withdrawn CSF 1.1 subcategories alongside the 106 active ones. The withdrawn entries are excluded because they are no longer part of the Core and cannot be rated.

## Framework columns

Copied from NIST. Identical for every organization assessing against CSF 2.0.

| Column | Type | Description |
|---|---|---|
| `function` | coded | One of GOVERN, IDENTIFY, PROTECT, DETECT, RESPOND, RECOVER |
| `category_id` | coded | Category identifier, for example GV.OC |
| `category_name` | prose | Category name, for example Organizational Context |
| `subcategory_id` | coded | Subcategory identifier and unique key for the row, for example GV.OC-01 |
| `subcategory_text` | prose | The outcome statement as published by NIST |

## Assessment columns

Specific to this environment. Filled during assessment.

| Column | Type | Allowed values | Governing section |
|---|---|---|---|
| `implementation_status` | coded | Fully Implemented, Largely Implemented, Partially Implemented, Not Implemented, Not Applicable | Section 5 |
| `rating_rationale` | prose | One or two sentences explaining the status | Section 5 |
| `assessment_depth` | coded | Evidence-backed, Rationale-only | Section 4 |
| `evidence_citation` | coded | GitHub URL pinned to a commit hash. Multiple citations separated by semicolons. Blank for Rationale-only rows | Section 9 |
| `na_justification` | prose | Required when status is Not Applicable. Names the specific function, asset class, or relationship that does not exist. Blank otherwise | Section 6 |
| `target_status` | coded | Same five values as `implementation_status`. Equals current status unless the gap is to be closed within the planning horizon | Section 8 |
| `priority` | coded | P1, P2, P3. Required only when `target_status` differs from `implementation_status`. Blank otherwise | Section 8 |
| `assessment_date` | coded | Date rated, YYYY-MM-DD. The target window for `priority` runs from this date | Section 11 |

## Reading a row

A row can be verified without reference to the assessor. `implementation_status` is the claim, `rating_rationale` is the reasoning, and `evidence_citation` is the proof. Where a citation is blank, `assessment_depth` reads Rationale-only, and the rating should be weighed as an assertion rather than a verified finding.

The POA&M is generated by filtering for rows where `target_status` differs from `implementation_status` and sorting by `priority`.
